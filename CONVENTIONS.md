## Задание

Собрать event-driven систему мониторинга новостей из RSS-лент нескольких российских информационных агентств

## Архитектура

Архитектура состоит из четырёх частей, связанных через очередь сообщений:
RSS-ленты агентств -> Monitor (poller + API, работает раз в 5 минут, есть ручка POST /refresh для ручного обновления) -> Worker (FastStream,  NER (SpaCy), запись в БД) -> PostgreSQL    

## Технологический стэк
Python 3.12;
пакетный менеджер — UV;
форматтер и линтер — ruff (после каждого изменения кода — ruff format и ruff check, все замечания исправлять);
хендлер воркера — на FastStream;
NER — SpaCy с русскоязычной моделью;
очередь и Postgres — только через docker-compose, никаких «ручных» локальных инсталляций в коде;
секреты и параметры подключения — из .env/settings, не хардкодить.

## Основные правила
 - файл CONVENTIONS.md не меняется
 - тесты для проверки проекта не меняются

## Работа сервиса
 - Event-driven, а не «монолит в цикле». Monitor и worker не должны знать друг о друге напрямую — только через очередь. Это позволяет масштабировать воркеры независимо.
 - Идемпотентность и дедупликация. Продумайте, что происходит при повторной доставке сообщения и при повторном опросе ленты. Уникальный ключ по link/guid в БД — простой предохранитель.
 - Загрузка SpaCy-модели. Модель тяжёлая — грузите её один раз при старте воркера, а не на каждое сообщение.
 - Обработка ошибок. Недоступная лента, битый XML, падение NER на одном сообщении не должны ронять весь сервис. Логируйте и продолжайте.
 - Методический слой. Сформулируйте вывод в духе урока: где двухшаговая схема (architect/editor, Plan/Act) реально сэкономила бюджет на этой сложной задаче, а где добавила лишнюю latency; как checkpoints/git-diff помогали откатывать неудачные шаги.
